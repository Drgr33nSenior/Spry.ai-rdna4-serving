# Sprint 32: 32K long-context SRE screen

Two repeated starts of the selected experimental profile completed 14 requests at a 32,768-token context setting. All responses stopped normally and all seven full output-ID and work pairs matched. The strict SRE grader passed only 2 of 12 long responses. The owner accepted the identified lexical exceptions for the current experimental session; the original strict failure remains in the record. This is not general 32K quality qualification.

Each start used one short warmup and six synthetic SRE cases: incident timeline and recovery evidence, and conditional runbook procedure, each with three evidence layouts. Long prompts contained 28,639–28,640 tokens, with a 4,096-token output cap and a 32-token reserve. Actual outputs were 514–1,127 tokens, so the run did not exercise the full context-plus-output boundary. The profile retained FP8 weights, BF16 target and draft KV, the selected b101 W4 kernel and aligned ring-fold with 19 usable/20 physical recurrent slots. No numerical kernel, production default or installed runtime changed.

The strict failures were lexical: six incident answers used `rolled back` where the oracle required `rollback`, and four runbook answers included `the` in ticket evidence where the oracle omitted it. The prompts requested source wording while the oracle used normalized labels. A retrospective audit found the factual fields matched in all 12 responses under those two exceptions; it does not replace the strict gate. The owner accepted these exceptions for current experimental use, without asserting a hardware cause or resolving the earlier numerical finding. See the [provenance record](../provenance/SPRINT32-LONG-CONTEXT-20261023.json).

The native command took 491.52 seconds. Non-streaming client elapsed times ranged from 14.83 to 22.21 seconds, with start medians of 18.16 and 18.11 seconds; these include prefill and generation. Time to first token and pure decode rate were not measured, and this is not a speed comparison with the prior short-workload benchmark.

Startup allocation was 21,008,233,472 bytes per card and driver-reported free memory was 11,886,657,536 bytes per card; neither is a whole-workload GPU peak. Host peaks were 30,606,680,064 and 24,612,687,872 bytes against a 40,802,189,312-byte limit, with no max or OOM events. Socket throttling counts were 10,756 and zero; their cause is not established. Independent release passed, and independent review approved the conservative closeout.

The next step is CPU preflight for 64K. The current split-KV adapter has a 32,768-token eligibility guard and falls back at 65,536. An extension and index, graph, slot, tokenizer and request-asset review are needed before a separately reviewed device screen. No 64K run has occurred. UltraQuant remains parked; BF16-weight comparison is deferred, with optional FP8 target KV and adaptive speculation after the context baseline. Endurance remains deferred.
